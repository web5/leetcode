# 数据库 · MySQL / InnoDB

---

**Q1：为什么 MySQL 索引用 B+ 树而不是哈希表、二叉树或 B 树？**

**A：**

- **哈希表**：等值查询 O(1) 极快，但**无序** → 无法做范围查询、`ORDER BY`、`LIKE 'x%'`、最左前缀，且哈希冲突后性能退化；
- **二叉搜索树/红黑树**：树太高（每个节点最多 2 个孩子），100 万数据就是 20 层，**每层一次磁盘 IO**，查询要 20 次 IO，不可接受；
- **B 树**：多路平衡（一个节点存多个 key），树高降到 3~4 层，但**每个节点都存数据**（行记录），节点能容纳的 key 少 → 树更高；且数据分散在各层，范围查询要做中序遍历（来回跨层）；
- **B+ 树**（InnoDB 的选择）：
  1. **非叶子节点只存索引 key，不存数据** → 单个 16KB 页能装下上千个 key → 树高仅 3 层就能存约 2000 万行（3 次 IO）；
  2. **叶子节点用双向链表相连** → 范围查询/全表扫描只需顺着链表扫，不用回到上层；
  3. 查询时间复杂度稳定 O(log N)，所有数据都在叶子层，IO 次数可预测。

> 3 层 B+ 树的容量估算：一个页 16KB，主键 bigint(8B) + 指针(6B) ≈ 14B → 每页约 1170 个 key；1170 × 1170 × 16（叶子每页约 16 行）≈ 2000 万行。

**Q2：聚簇索引、二级索引、回表、覆盖索引是什么？**

**A：**

- **聚簇索引（clustered）**：InnoDB 的主键索引，叶子节点存**整行数据**，表数据本身按主键顺序组织（一张表只有一个）；
- **二级索引（secondary）**：普通索引/唯一索引，叶子节点存的是**索引列 + 主键值**；
- **回表**：通过二级索引拿到主键后，再去聚簇索引查整行 → 多一次 B+ 树查询（随机 IO，慢）；
- **覆盖索引**：查询的列都在索引里，无需回表 → `EXPLAIN` 的 Extra 出现 `Using index`，是重要优化手段；
- 无显式主键时：InnoDB 选第一个非 NULL 唯一索引，否则生成 6 字节隐藏 `ROWID`。

> 实践：主键建议**自增 bigint**（顺序插入，页分裂少、碎片少），避免用 UUID 做主键（随机写导致频繁页分裂、页利用率下降）。

**Q3：最左前缀原则是什么？哪些情况会导致索引失效？**

**A：** 联合索引 `(a, b, c)` 的 B+ 树按 a 排序、a 相同按 b、再按 c。所以只能从**最左列开始连续匹配**：

- `WHERE a=1 and b=2` ✅、`a=1 and b=2 and c=3` ✅、`a=1 order by b` ✅；
- `WHERE b=2` ❌（跳过了 a，无法定位）；
- `WHERE a=1 and c=3` → 只用上 a（b 断掉了，c 用不上）；
- 范围条件右边的列失效：`a>1 and b=2` 中 b 无法用于定位（只能过滤）。

常见失效场景：

1. 索引列上做**函数/运算/隐式类型转换**（`where DATE(created_at)=...`、`where id+1=5`、字符串列传数字导致 `CAST`）；
2. `LIKE '%abc'` 前置通配符；
3. `OR` 连接的列中有的没索引；
4. 违反最左前缀、使用了 `!=` / `NOT IN` / `IS NULL`（视数据分布）；
5. 优化器判断**回表成本高于全表扫描**（如区分度极低的"性别"列）→ 主动放弃索引，这其实是优化器的正确选择。

**Q4：事务的 ACID 是怎么实现的？**

**A：**

| 特性 | 含义 | InnoDB 实现 |
| --- | --- | --- |
| **A 原子性** | 要么全做，要么全不做 | **undo log**：修改前记录旧值，回滚时反向恢复 |
| **C 一致性** | 从一个合法状态到另一个合法状态 | 由 A/I/D 共同保证 + 约束（主键/外键/唯一/check） |
| **I 隔离性** | 并发事务互不干扰 | **锁**（并发写）+ **MVCC**（读写不冲突） |
| **D 持久性** | 提交后即使宕机也不丢 | **redo log**：先写日志再刷页（WAL），崩溃后重放 |

三驾马车：**undo log（回滚 + MVCC）→ redo log（崩溃恢复）→ binlog（主从复制/归档）**。

**Q5：事务的隔离级别？分别解决什么问题？**

**A：**

| 级别 | 脏读 | 不可重复读 | 幻读 | 实现要点 |
| --- | --- | --- | --- | --- |
| 读未提交 RU | ✗ 有 | ✗ 有 | ✗ 有 | 直接读最新，几乎不用 |
| 读已提交 RC | ✅ 解决 | ✗ 有 | ✗ 有 | 每条 SQL 生成新 ReadView（Oracle/ PG 默认） |
| **可重复读 RR** | ✅ | ✅ | ✅（快照读）/ 需 next-key 锁（当前读） | 事务首个快照读生成 ReadView，之后复用（**MySQL 默认**） |
| 串行化 Serializable | ✅ | ✅ | ✅ | 读写都加锁，并发度最低 |

三个问题：

- **脏读**：读到别人**未提交**的修改；
- **不可重复读**：同一事务两次读，结果值不同（别人**已提交**的 UPDATE/DELETE）；
- **幻读**：同一事务两次范围查询，行数变了（别人 INSERT 了新行）。

**Q6：MVCC 是怎么实现的？**

**A：** MVCC（多版本并发控制）让**读不加锁、读写不冲突**，依赖三件套：

1. **隐藏列**：每行有 `DB_TRX_ID`（最后修改该行的事务 ID）、`DB_ROLL_PTR`（指向 undo log 的回滚指针）、`DB_ROW_ID`；
2. **undo log 版本链**：每次 UPDATE 把旧值写进 undo，并用 ROLL_PTR 串成链表，形成该行的历史版本；
3. **ReadView（一致性视图）**：事务快照读时生成，包含 `m_ids`（当前活跃事务列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。

可见性判定（简化）：

- `trx_id < min_trx_id` → 已提交，**可见**；
- `trx_id > max_trx_id` → 未来事务，**不可见**；
- 在活跃列表里 → 未提交，**不可见**；否则可见。
- 不可见就顺着 ROLL_PTR 找上一个版本，直到可见为止。

**RC vs RR 的差别就在 ReadView 生成时机**：RC 每条语句生成一次；RR 只在事务第一次快照读生成，之后沿用 → 所以 RR 下"可重复读"。

> MVCC 只解决**快照读**的幻读；`SELECT ... FOR UPDATE` 这类**当前读**靠 **next-key lock** 防幻读。

**Q7：InnoDB 有哪些锁？**

**A：**

按粒度：

- **行锁**：`Record Lock`（锁单条索引记录）、`Gap Lock`（锁记录之间的间隙，防止插入）、**`Next-Key Lock` = Record + Gap**（左开右闭区间，RR 下默认，防幻读）、`Insert Intention Lock`（插入意向锁）；
- **表锁**：`LOCK TABLES`、DDL 的元数据锁 MDL（**长事务会阻塞 DDL**，线上加字段要小心）、`AUTO-INC Lock`；
- **意向锁 IS/IX**：表级标记"某行将被共享/排他锁"，用于快速判断表级冲突。

按类型：**共享锁 S**（`SELECT ... LOCK IN SHARE MODE`）、**排他锁 X**（`UPDATE/DELETE`、`FOR UPDATE`）。

加锁规则要点：

- 行锁是**加在索引上**的，没走索引会退化成锁全表所有行（等同表锁）；
- RR 下对**非唯一索引**的范围扫描会加 next-key lock，等值查询命中唯一索引时退化为记录锁；
- 死锁时 InnoDB 用**等待图**检测，回滚 undo 量较小的事务；`innodb_lock_wait_timeout`（默认 50s）兜底。

**Q8：binlog、redo log、undo log 的区别？两阶段提交是什么？**

**A：**

| | redo log | undo log | binlog |
| --- | --- | --- | --- |
| 层 | InnoDB 引擎层 | InnoDB 引擎层 | **Server 层**（所有引擎） |
| 类型 | 物理日志（"某页某偏移改成什么"） | 逻辑日志（"旧值是什么"） | 逻辑日志（SQL 语句/行前后镜像） |
| 作用 | **崩溃恢复**，保证持久性 | **回滚** + MVCC 版本链 | **主从复制**、数据恢复/审计 |
| 写入 | 循环写（固定大小，checkpoint 覆盖） | 随事务产生 | 追加写，可归档 |
| 刷盘 | `innodb_flush_log_at_trx_commit`：1=每次提交刷盘（最安全）、2=写 OS 缓存、0=每秒刷 | — | `sync_binlog`：1 最安全 |

**两阶段提交（2PC）**：为了让 redo 与 binlog **状态一致**（否则主从不一致），提交分两步：

1. `prepare`：redo log 写入并刷盘，标记 prepare；
2. 写 binlog 并刷盘；
3. `commit`：redo log 标记 commit。

崩溃恢复时：redo 处于 prepare 且 binlog 完整 → **提交**；binlog 不完整 → **回滚**。

**Q9：`EXPLAIN` 主要看哪些字段？**

**A：**

- **`type`（最重要，从好到坏）**：`system > const > eq_ref > ref > range > index > ALL`；至少要到 `range`，避免 `ALL`（全表扫描）；
- **`key`**：实际用到的索引（与 `possible_keys` 对比，看是否选错）；
- **`rows`**：预估扫描行数，越小越好；
- **`Extra`**：`Using index`（覆盖索引，好）、`Using where`、`Using filesort`（需额外排序，考虑加索引）、`Using temporary`（临时表，常见于 `GROUP BY`/`DISTINCT`，需优化）；
- `key_len`：用到的索引字节数，可判断是否用满联合索引；
- `filtered`：过滤比例。

> MySQL 8 加分项：`EXPLAIN ANALYZE`（真实执行 + 耗时）、`EXPLAIN FORMAT=JSON`、Optimizer Trace 看优化器为什么选错索引。

**Q10：常见的 SQL / 索引优化手段？**

**A：**

1. **建合适的索引**：区分度高的列、联合索引按「查询频率 + 区分度」排最左、优先**覆盖索引**避免回表；
2. **避免索引失效**：不做函数运算、注意隐式类型转换、不用 `%` 开头模糊查询；
3. **分页优化**：`LIMIT 1000000, 10` 会扫描并丢弃前 100 万行 → 用**延迟关联**或**游标分页**（`WHERE id > last_id LIMIT 10`）；
4. **排序/分组**：让 `ORDER BY/GROUP BY` 走索引顺序，避免 `filesort` 和临时表；
5. **只查需要的列**：避免 `SELECT *`（更多回表、更多网络传输、无法覆盖索引）；
6. **批量操作**：`INSERT ... VALUES (...),(...)`、分批提交，减少事务与网络往返；
7. **拆分大事务**：长事务会持有锁、撑爆 undo、阻塞 purge；
8. **数据类型尽量小**：`INT` 而非 `BIGINT`、NOT NULL + 默认值，行越小一页装得越多，树越矮。

**Q11：一条慢 SQL 怎么排查？**

**A：**

1. **定位**：开慢查询日志（`slow_query_log`、`long_query_time`）或用 APM/performance_schema 抓到具体 SQL；
2. **看执行计划**：`EXPLAIN` / `EXPLAIN ANALYZE`，重点看 type、key、rows、Extra；
3. **看扫描/返回比**：`Handler_read_%` 状态变量、慢日志的 `Rows_examined / Rows_sent`，比值大说明过滤条件没走索引；
4. **判断阻塞**：`SHOW PROCESSLIST` / `information_schema.innodb_trx` 看是否有锁等待、长事务；
5. **对症下药**：加/改索引 → 改 SQL 写法 → 拆查询或加缓存 → 最后才考虑改表结构/分库分表；
6. **验证**：改完对比 `EXPLAIN` 与实际耗时，注意统计信息要准确（`ANALYZE TABLE`，`innodb_stats_persistent`）。

**Q12：`COUNT(*)`、`COUNT(1)`、`COUNT(列)` 的区别？**

**A：**

- `COUNT(*)`：统计**行数**，InnoDB 会选一个最小的二级索引来扫（MySQL 8 已优化），不读整行；
- `COUNT(1)`：与 `COUNT(*)` 在 InnoDB 下**基本等价**，优化器同样处理（无性能差异）；
- `COUNT(列)`：统计该列**非 NULL** 的行数，需要判断 NULL；
- `COUNT(id)` 走主键索引，通常比走二级索引的 `COUNT(*)` 慢（主键更大、一页装得少）。

> 大表精确行数很慢（MVCC 下每行可见性要判断，不能像 MyISAM 直接存 count）。优化：用近似值（`information_schema.TABLES.TABLE_ROWS`）、Redis 计数器、或单独的计数表。

**Q13：主从复制的原理与延迟问题？**

**A：** 原理（异步复制）：

1. 主库把变更写 **binlog**（dump 线程）；
2. 从库 `IO 线程` 拉取 binlog 写入本地 **relay log**；
3. 从库 `SQL 线程` 回放 relay log（MySQL 5.6+ 可并行回放，按库或按组提交）。

复制格式：`STATEMENT`（SQL 语句，体积小但可能有不确定性）、`ROW`（行前后镜像，安全、体积大，**推荐**）、`MIXED`。

**主从延迟的常见原因与对策**：

- 从库**单线程回放**跟不上主库并发写 → 开启并行复制（`slave_parallel_workers`，8.0 的 `writeset`）；
- 大事务（一次删 100 万行）→ 拆小事务；
- 从库承担大量读查询、配置差 → 扩容/限流；
- 无主键表导致 ROW 模式回放慢 → 加主键。

读写分离下的**读不到刚写的数据**：关键写后读走主库，或等 `seconds_behind_master=0`，或用 GTID 等待（`WAIT_FOR_EXECUTED_GTID_SET`）。

**Q14：三大范式是什么？实际设计要不要严格遵守？**

**A：**

- **1NF**：字段原子不可再分（不能一列存多个值）；
- **2NF**：在 1NF 基础上，非主属性**完全依赖**主键（消除部分依赖，主要针对联合主键）；
- **3NF**：非主属性不**传递依赖**于主键（如"订单表存了用户所在城市"，城市依赖用户而非订单）。
- BCNF：主属性也不能部分/传递依赖于候选键。

**现实做法：适度反范式**。为了减少 JOIN、提升查询性能，允许冗余字段（如订单表冗余商品名、统计字段），代价是要保证一致性（双写、异步补偿、触发器）。常见取舍：

- 读多写少 → 冗余换查询速度；
- 写多/一致性要求高 → 保持范式，靠索引和缓存解决性能。

**Q15：`CHAR` vs `VARCHAR`？`DELETE`/`TRUNCATE`/`DROP` 的区别？**

**A：**

- **CHAR(n)**：定长，不足补空格，读取时去掉尾部空格；适合固定长度（MD5、手机号、状态码），更新不易产生碎片，但浪费空间；
- **VARCHAR(n)**：变长，额外 1~2 字节记录长度；省空间，但更新变长可能引发**页分裂**；`n` 是**字符数**（utf8mb4 一个汉字占 4 字节，`VARCHAR(10)` 最多 40 字节）。

| | DELETE | TRUNCATE | DROP |
| --- | --- | --- | --- |
| 类型 | DML | DDL | DDL |
| 可回滚 | ✅（在事务内） | ❌ 隐式提交 | ❌ |
| 可带 WHERE | ✅ | ❌ | ❌ |
| 原理 | 逐行标记删除（走 undo/redo，慢） | 重建表/释放数据页，快 | 删表结构与数据 |
| 自增 | 不重置 | **重置** | — |

> 大表清理用分批 `DELETE LIMIT` 或 `pt-archiver`，避免长事务撑爆 undo 和主从延迟。
