# 数据库 · Redis

---

**Q1：Redis 有哪些数据类型？各自使用场景？**

**A：**

| 类型 | 结构 | 典型场景 |
| --- | --- | --- |
| **String** | 字符串/整数/浮点，最大 512MB | 缓存、分布式锁（`SET NX PX`）、计数器（`INCR`）、限流、Session |
| **Hash** | field-value 映射 | 对象存储（用户信息、购物车），可单独改字段 |
| **List** | 有序可重复 | 消息队列（`LPUSH`+`BRPOP`）、最新列表、栈 |
| **Set** | 无序去重 | 标签、共同好友（`SINTER`）、抽奖（`SRANDMEMBER`）、去重 |
| **ZSet** | member + score | **排行榜**、延迟队列（score=时间戳）、优先级队列 |
| **BitMap** | 位数组 | 签到、活跃用户统计（1 亿用户日活约 12.5MB） |
| **HyperLogLog** | 概率计数 | UV 统计（0.81% 误差，固定 12KB） |
| **GEO** | 经纬度（基于 ZSet） | 附近的人、附近门店 |
| **Stream** | 消息流（5.0+） | 真正的消息队列：消费组、ACK、PEL、持久化 |

---

**Q2：Redis 底层数据结构有哪些？**

**A：** "数据类型"与"底层实现"是两层（可用 `OBJECT ENCODING key` 查看）：

- **SDS**（简单动态字符串）：带 `len`/`alloc` → O(1) 取长度、二进制安全、预分配与惰性释放减少内存重分配；
- **dict 哈希表**：数组 + 链地址法，扩容用**渐进式 rehash**（同时持有 ht[0]/ht[1]，每次操作搬一批），避免一次性搬迁卡住主线程；
- **skiplist 跳表**：多层索引链表，ZSet 元素多时用「跳表（范围查询 O(logN)）+ dict（按 member 查 score O(1)）」组合；
- **ziplist → listpack**：连续内存的紧凑列表，省指针开销，元素少且小时用于 Hash/ZSet；Redis 7 用 listpack 取代 ziplist（消除**级联更新**问题）；
- **quicklist**：List 底层 = 双向链表 + 每节点一个 listpack；
- **intset**：Set 元素全为整数且数量少时的编码，有序、二分查找。

> 为什么 ZSet 用跳表不用红黑树：跳表实现简单、范围查询天然友好（顺着前进指针扫）、插入只改局部指针，不用旋转再平衡。

**Q3：RDB 和 AOF 的区别？怎么选？**

**A：**

| | RDB | AOF |
| --- | --- | --- |
| 内容 | 某一时刻的**内存快照**（二进制压缩） | 逐条写命令（文本协议） |
| 触发 | `save`/`bgsave`、配置 `save 900 1`、主从全量复制、shutdown | 每次写后（`appendfsync` 控制刷盘：always/everysec/no） |
| 文件 | 小、恢复**快** | 大、恢复慢（要重放命令） |
| 安全性 | 会丢最后一次快照之后的数据 | `everysec` 最多丢 1 秒 |
| 影响 | `bgsave` 用 `fork` + COW，内存峰值时可能卡顿 | 追加写，但需要 **AOF 重写**（`BGREWRITEAOF`）瘦身 |

**生产做法：两者都开**。Redis 4.0+ 支持**混合持久化**：AOF 重写时把当前数据以 RDB 格式写入 AOF 文件开头，后续增量命令仍以 AOF 格式追加 → 既快又安全。

> 坑：`fork` 本身会阻塞（页表拷贝，大实例可达百毫秒级），且 COW 期间内存可能翻倍 → 控制单实例大小（一般 ≤ 10GB）、关闭 THP（`transparent_hugepage`）、保证有 swap。

**Q4：Redis 的过期删除策略和内存淘汰策略？**

**A：**

**过期删除**（三者配合）：

1. **惰性删除**：访问 key 时才判断是否过期并删除（省 CPU，但冷数据占内存）；
2. **定期删除**：默认每秒 10 次随机抽样检查（`ACTIVE_EXPIRE_CYCLE`），删除已过期的；
3. 内存达到 `maxmemory` 时触发**淘汰**。

> 补充：从库**不会**主动删过期 key，靠主库同步 `DEL`；3.2 起从库读时会返回 NULL，逻辑上过期。

**内存淘汰策略（8 种）**：

- `noeviction`（默认）：不淘汰，写操作直接报错（生产一般不用）；
- `volatile-ttl`：在设了过期时间的 key 中淘汰剩余 TTL 最短的；
- `volatile-random` / `allkeys-random`：随机；
- **`allkeys-lru`**：所有 key 中淘汰最近最少用的（**纯缓存场景最常用**）；
- `volatile-lru`：只在设了过期时间的 key 中 LRU；
- `allkeys-lfu` / `volatile-lfu`（4.0+）：淘汰访问频次最低的，适合有"热点长期稳定"的场景。

> Redis 的 LRU/LFU 都是**近似**实现：随机采样 N 个（`maxmemory-samples`，默认 5）取最优，避免维护全局链表的开销。

**Q5：缓存穿透、击穿、雪崩分别是什么？怎么解决？**

**A：**

- **穿透**：查询**根本不存在的 key**（如恶意 id=-1），缓存永不命中，请求直穿数据库。
  - 解法：① 参数校验/限流；② **布隆过滤器**（存在性预检，注意有误判率、删除困难，可用 Cuckoo Filter）；③ **缓存空值**（`SET key "" 短TTL`）。
- **击穿**：**单个热点 key** 过期的瞬间，海量并发同时回源，打爆数据库。
  - 解法：① 热点 key **不设过期**（逻辑过期 + 后台刷新）；② **互斥重建**（分布式锁，只让一个请求回源，其他等待/返回旧值）；③ 提前预热 + 随机 TTL。
- **雪崩**：**大批 key 同时过期** 或 **Redis 集群整体不可用**，流量全打到 DB。
  - 解法：① TTL 加**随机抖动**（`TTL + random(0,300)`）；② Redis 高可用（哨兵/集群）+ 多级缓存（本地 Caffeine + Redis）；③ 服务**降级/熔断/限流**（返回兜底数据）。

**Q6：如何保证缓存与数据库的一致性？**

**A：** 没有强一致的完美方案，只有适合业务的选择：

1. **Cache Aside（旁路缓存，最常用）**：
   - 读：先读缓存，命中返回；未命中读 DB 再写入缓存；
   - 写：**先更新数据库，再删除缓存**（而不是更新缓存 —— 避免并发写导致的脏数据、也避免无用计算）。
2. **为什么是删缓存而不是更新缓存**：两个并发写顺序错乱会让缓存存的是旧值；且有些缓存值计算成本高、可能没人读。
3. **潜在不一致**：读请求未命中 → 查到旧值 → 此时写请求更新 DB 并删缓存 → 读请求把旧值写入缓存。概率较低（需要读比写慢），可用**延迟双删**（删 → 更新 DB → sleep 一小段 → 再删）或 **MQ 重试删除** 兜底。
4. **强一致场景**：用分布式锁串行化，或用 **Canal 监听 binlog 异步删除**（把缓存维护解耦出去，更可靠）；或读走主库 + 事务提交后再删缓存。
5. 兜底：给缓存加较短 TTL，最终一致。

**Q7：Redis 怎么做分布式锁？有什么坑？**

**A：**

```
SET lock:order:123 <uuid> NX PX 30000     # 加锁（原子：设值 + 过期）
# 释放：用 Lua 保证「判断 value + 删除」原子性
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end
```

关键点与坑：

1. **必须一条命令加锁**（`SET NX PX`），不能 `SETNX` 后再 `EXPIRE`（中间崩溃会死锁）；
2. **必须设过期时间**，防止持有者宕机导致锁永不释放；
3. **释放要校验 value（uuid）**，避免误删别人的锁；且校验与删除必须原子（Lua）；
4. **业务执行时间 > 锁过期时间** → 提前解锁，别人趁虚而入 → 用**看门狗自动续期**（Redisson `watchdog`，默认每 10s 续到 30s）；
5. **单点/主从切换丢锁**：主库加锁后未同步就从库升主 → 两个客户端同时持锁 → 场景要求高时用 **Redlock**（N 个独立节点，半数以上 + 总耗时小于 TTL 才算成功），但 Redlock 在时钟漂移/GC 停顿上有争议（Martin Kleppmann 的批评），一般用业务层幂等 + 数据库兜底更稳；
6. 可重入：用 Hash 结构记录 `uuid:重入次数`（Redisson 的做法）。

**Q8：主从复制、哨兵、集群的区别？**

**A：**

- **主从复制**：一主多从，数据单向同步（`replicaof`）；作用：读写分离、数据备份。故障时**需人工切换**。
- **哨兵 Sentinel**：在主从之上加监控进程，负责**监控 + 自动故障转移 + 通知**；客户端通过哨兵获取当前主节点地址。适合数据量不大（单实例能装下）、要高可用的场景；缺点：不能水平扩容、写仍单点。
- **Cluster 集群（官方，3.0+）**：**去中心化**，16384 个哈希槽（slot）分配到各主节点，`CRC16(key) % 16384` 定位；支持多主同时写、水平扩容、自动故障转移（Gossip + 主从切换）。

> Cluster 细节：key 用 **hash tag**（`{}` 包裹）可强制落在同一槽以支持多 key 操作；扩容用 `CLUSTER ADDSLOTS`/迁移槽；客户端需支持 `MOVED/ASK` 重定向（Jedis Cluster、Lettuce、go-redis 都支持）。

**Q9：Redis 事务和 Lua 脚本？**

**A：**

- **事务**：`MULTI` 入队 → `EXEC` 顺序执行。`WATCH` 提供乐观锁（被监视 key 被改则 EXEC 返回 nil，需重试）。
- **Redis 事务不保证原子回滚**：语法错误（入队时发现的）会整体不执行；但**运行时错误**（如对 String 做 `LPUSH`）不会回滚其他命令 —— 这是与关系型数据库事务的最大区别。
- **Lua 脚本**：`EVAL`/`EVALSHA` 在服务端原子执行一段脚本（执行期间不处理其他命令），适合"读-判断-写"复合操作，比事务更强大、更省网络往返。

> 注意：脚本必须短小（会阻塞主线程），禁止死循环和慢命令；长脚本会触发 `busy` 保护，需 `SCRIPT KILL`。

**Q10：Pipeline 是什么？和 Lua、MGET 有什么区别？**

**A：**

- **Pipeline**：把多条命令打包一次发送、一次收回应答，**省掉 N 次网络 RTT**，但命令之间**不是原子**的（中间可插入其他客户端命令）。适合批量写入/读取、无依赖的场景。
- **MGET / MSET**：单条命令处理多个 key，**原子**且更省，但只能用于同类型简单操作。
- **Lua 脚本**：需要"读-算-写"复合且**要求原子**时用。

> 注意：Pipeline 打包命令过多会占用输出缓冲、阻塞连接 → 分批（如每批 500 条）。

**Q11：什么是大 key、热 key？怎么处理？**

**A：**

- **大 key**：value 过大（String > 10KB）或元素过多（Hash/Set/ZSet/List 元素 > 1 万）。
  - 危害：读写耗时阻塞主线程、网络传输慢、**删除时同步释放内存造成卡顿**、分片集群数据倾斜、fork 时页表大。
  - 处理：拆分（如按 id 取模拆成多个 Hash）、压缩 value、**异步删除 `UNLINK`**（Redis 4+ 惰性释放）、用 `SCAN` 代替 `KEYS`。
- **热 key**：某个 key 的 QPS 极高（明星动态、秒杀商品），集中在单个实例。
  - 危害：单分片 CPU/带宽打满，扩容都不能解决（还是打同一台）。
  - 处理：**本地缓存**（Caffeine/Guava + 短 TTL）、key 加随机后缀拆到多个分片（读写时聚合）、读写分离、限流。
- 发现手段：`redis-cli --bigkeys`、`--hotkeys`（需 `maxmemory-policy` 为 LFU）、`MEMORY USAGE key`、监控 `latency` 与分片流量倾斜。

**Q12：Redis 6.0 的多线程是怎么回事？**

**A：** Redis 6.0 引入多线程，但**只用于网络 IO 的读写与协议解析**（`io-threads N`），**命令执行仍然单线程**。所以：

- 不再有锁竞争与原子性问题；
- 主要收益在大报文、高连接数的场景（解析/回包成为瓶颈时）；
- 小包场景收益有限，官方建议 `io-threads` 设为 2~4（机器核数的一半左右），过多反而因自旋等待变慢。

真正的"后台多线程"其实一直有：`BGSAVE`、`UNLINK`、AOF fsync、惰性删除都有 bio 线程。

**Q13：Redis 和 Memcached 怎么选？**

**A：**

| 维度 | Redis | Memcached |
| --- | --- | --- |
| 数据类型 | 丰富（String/Hash/List/Set/ZSet/Stream...） | 仅 String |
| 持久化 | 支持（RDB/AOF） | 不支持（纯缓存） |
| 线程模型 | 单线程执行命令（6.0 网络 IO 多线程） | **多线程**，多核利用更好 |
| 内存管理 | 自己的分配器，可能碎片 | Slab 预分配，无碎片但可能浪费 |
| 分布式 | 官方 Cluster | 客户端一致性哈希 |
| 其他能力 | 事务、Lua、发布订阅、Stream、GEO、位图 | 简单 |

选 Memcached 的场景几乎只剩"极简 KV + 需要吃满多核 + 大 value 缓存"；绝大多数业务选 Redis。
