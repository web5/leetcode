# 计算机组成原理 · 编译链接

---

**Q1：冯诺依曼体系结构是什么？瓶颈在哪？**

**A：** 五大部件：**运算器 + 控制器（CPU）、存储器、输入设备、输出设备**。核心思想：

1. **存储程序**：指令与数据存放在同一存储器，按地址访问；
2. **顺序执行**：取指 → 译码 → 执行，PC 自动加一。

**冯诺依曼瓶颈**：CPU 与内存速度差两个数量级（CPU 周期 ~0.3ns，内存访问 ~60-100ns），指令与数据共享总线，CPU 大量时间在等数据 → 靠**多级缓存、流水线、分支预测、预取**缓解。哈佛结构（指令与数据分开）用于 MCU/DSP，也用于 CPU 内部 L1 的 I-Cache/D-Cache 分离。

---

**Q2：一条指令在 CPU 里怎么执行？**

**A：** 经典五级流水线（MIPS）：**取指 IF → 译码 ID → 执行 EX → 访存 MEM → 写回 WB**。各阶段用不同硬件，理想情况每周期完成一条指令。

三种冒险（hazard）会打断流水线：

- **结构冒险**：硬件资源冲突（同时访存）→ 加资源或 I/D Cache 分离；
- **数据冒险**：后一条要用前一条的结果 → **转发/旁路（forwarding）**，不行就插入气泡 stall；
- **控制冒险**：分支未决，不知下一条取谁 → **分支预测**（BTB + 两级自适应，命中率 >95%），预测失败要清空流水线（代价 10~20 周期）。

现代 CPU 更进一步：超标量（多发射）、乱序执行（Tomasulo + ROB）、寄存器重命名、SIMD。

---

**Q3：CPU Cache 为什么有效？映射方式有哪些？**

**A：** 有效性来自**局部性原理**：

- **时间局部性**：刚访问的数据很可能再访问（循环变量）；
- **空间局部性**：访问某地址后，附近地址很可能被访问（数组遍历）→ 按 **Cache Line（64B）** 整块加载。

| 映射方式 | 规则 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 直接映射 | 主存块 → 唯一固定行 | 简单快 | 冲突抖动严重 |
| 全相联 | 可放任意行 | 冲突最少 | 比较电路昂贵 |
| **组相联**（主流） | 先定组，组内全相联 | 折中（8/16 路） | — |

替换策略：LRU / 随机 / PLRU。写策略：**写直达**（同时写内存，简单慢）vs **写回**（只写 Cache，淘汰时写回，配 dirty bit，主流）。

> 经典性能题：遍历二维数组，按行访问比按列快数倍 —— 因为按列会跨 Cache Line、Cache 命中率暴跌。

**Q4：什么是伪共享（False Sharing）？怎么避免？**

**A：** 两个线程分别修改**同一个 Cache Line 中的不同变量**时，虽然逻辑上无共享，但缓存一致性协议（MESI）以 Cache Line 为单位，任一变量被改都会让对方核心的整行失效 → 反复从内存/其他核心重新加载，性能骤降。

避免方法：

1. **填充 padding**：把变量扩到 64 字节（Java 8 的 `@Contended`、Disruptor 的 `Sequence` 前后各 7 个 long）；
2. 让不同线程操作的数据在内存上远离（按 core 数分槽，`LongAdder` 的 Cell 数组就是分散槽位）；
3. 只读共享没问题（都在 S 状态）。

> 反面例子：一个 `volatile long[]` 数组，多线程各改自己的下标，若下标相邻仍会互相影响。

---

**Q5：什么是 MESI 协议？**

**A：** 多核缓存一致性协议，Cache Line 有四种状态：

- **M (Modified)**：已修改，与内存不一致，仅本核有副本；
- **E (Exclusive)**：干净，仅本核有，与内存一致；
- **S (Shared)**：多核共享，与内存一致；
- **I (Invalid)**：无效。

转换要点：写 S/E → 发 `Invalidate` 让其他副本变 I，自己变 M；其他核读 M 状态时，要**写回内存或转发**给对方。为避免每次写都要等总线响应，引入了 **Store Buffer + Invalid Queue**（也是内存可见性问题/需要内存屏障的根因）。RVMO / x86-TSO 内存模型差异就在这里。

**Q6：大端和小端是什么？怎么判断？**

**A：**

- **大端 Big Endian**：高位字节存在**低地址**（符合人类阅读习惯），网络字节序就是大端；
- **小端 Little Endian**：低位字节存低地址，x86/ARM（多数模式）用。

例：`0x12345678` 在地址 0x100 起，大端存 `12 34 56 78`，小端存 `78 56 34 12`。

判断方法：`union { int i; char c; }` 取 `c == 1` 则为小端；或 `*(char*)&i`。

实践意义：**网络传输必须转网络字节序**（`htons/htonl`），跨平台文件格式/协议解析要显式处理字节序。

**Q7：为什么用补码表示负数？**

**A：** 补码定义：正数的补码是自身；负数的补码 = 其绝对值**按位取反 + 1**（或 `2^n - |x|`）。

用补码的三个好处：

1. **0 的表示唯一**：原码/反码都有 `+0` 和 `-0`，补码只有一个 `0000...0`；
2. **加减法统一**：`a - b` 直接等于 `a + (-b 的补码)`，CPU 不需要减法器，符号位一起参与运算；
3. 多表示了一个数：n 位补码范围是 `[-2^(n-1), 2^(n-1)-1]`（如 int8：-128 ~ 127）。

> 溢出陷阱：`127 + 1 = -128`（有符号回绕）；比较 `i < strlen(s)` 时 `strlen` 返回 `size_t`（无符号）会触发**隐式类型提升**导致死循环。

**Q8：浮点数为什么有精度问题？0.1 + 0.2 !== 0.3？**

**A：** IEEE 754 双精度（64 位）= 1 位符号 + 11 位指数 + 52 位尾数（隐含 1 位，共 53 位有效位）。

- 十进制的 `0.1` 在二进制里是**无限循环小数**（类似 1/3 在十进制），只能截断存储 → 天生有误差；
- `0.1 + 0.2 = 0.30000000000000004`，与 `0.3` 的二进制表示不同 → 不相等。

正确做法：

1. 比较用**误差范围**：`Math.abs(a - b) < Number.EPSILON * k`；
2. 金额用**整数分**存储（`cents`）或 `decimal`/`BigDecimal`；
3. 不要用 `float/double` 做等值比较、不要用浮点做循环计数器。

> 整数安全范围：`Number.MAX_SAFE_INTEGER = 2^53 - 1`，超过就会丢失精度（后端雪花 ID 到前端必须转字符串）。

**Q9：C/C++ 程序从源码到可执行文件经历了什么？**

**A：** 四步：

1. **预处理（`.c → .i`）**：展开 `#include`、宏替换、`#ifdef` 条件编译、删除注释（`gcc -E`）；
2. **编译（`.i → .s`）**：词法分析 → 语法分析（AST）→ 语义分析 → **中间代码 + 优化** → 生成汇编（`gcc -S`）；
3. **汇编（`.s → .o`）**：汇编指令翻译成机器码，生成**可重定位目标文件**（含符号表、重定位表、各段 `.text/.data/.bss`）；
4. **链接（`.o → 可执行文件`）**：
   - **符号解析**：把每个符号引用绑定到一个定义；
   - **重分配/重定位**：合并同类型段、分配运行时地址、修正引用处的地址。

> 常见错误对照：预处理错 → 找不到头文件；编译错 → 语法/类型错误；链接错 → `undefined reference`（声明了没定义/没链接库）、`multiple definition`（重复定义）。

**Q10：静态链接和动态链接的区别？**

**A：**

| | 静态链接（`.a`/`.lib`） | 动态链接（`.so`/`.dylib`/`.dll`） |
| --- | --- | --- |
| 时机 | 编译期把库代码拷进可执行文件 | 运行时由动态链接器加载 |
| 体积 | 大（每个程序一份拷贝） | 小，**多进程共享**同一份物理内存 |
| 启动 | 快（无需加载） | 稍慢（符号重定位，可用 PLT 延迟绑定） |
| 升级 | 要重新编译整个程序 | 换 `.so` 即可（注意 ABI 兼容） |
| 部署 | 简单，无依赖 | 依赖库版本（"依赖地狱"，Linux 用 `ldd` 排查） |

> **位置无关代码 PIC**：`.so` 要能被加载到任意地址，用 GOT/PLT 做间接寻址；`-fPIC` 就是为此。

**Q11：栈帧里有什么？函数调用发生了什么？**

**A：** 一次调用（以 x86-64 为例）：

1. 前 6 个参数放寄存器（`rdi, rsi, rdx, rcx, r8, r9`），多的压栈；
2. `call` 指令：**把返回地址压栈** 并跳转；
3. 被调函数序言（prologue）：`push rbp; mov rbp, rsp; sub rsp, N` —— 建立新栈帧，给局部变量分配空间；
4. 执行函数体；
5. 尾声（epilogue）：`mov rsp, rbp; pop rbp; ret` —— 恢复栈帧，从栈上弹出返回地址跳回。

栈帧内容：返回地址、上一个 `rbp`、局部变量、临时值、寄存器保存区、对齐填充。

> 递归太深 → 栈溢出；局部变量过大（如 `char buf[10MB]`）也会爆栈，要放堆上。

**Q12：内存对齐是什么？为什么要对齐？**

**A：** 变量的起始地址必须是自身大小（或对齐系数）的整数倍。例如 `struct { char a; int b; }`，`a` 在 0，`b` 必须 4 字节对齐 → 偏移 4，结构体总大小 8（而非 5）。

原因：

1. **硬件**：多数 CPU 只能从对齐地址读取多字节数据，未对齐访问可能触发异常或需要多次访存拼装（慢）；
2. **Cache**：不对齐的字段可能横跨两个 Cache Line，多一次访问甚至引发原子性问题；
3. 某些架构（SPARC、部分 ARM）完全不支持非对齐访问。

实践：结构体里**把大类型放前面**（或按大小降序排列）能减少 padding；网络协议/文件格式通常用 `#pragma pack(1)` 紧凑排列，但要付出性能代价。

> 位域、原子变量（`std::atomic`）的对齐还关系到 CPU 原子性保证。
