# 操作系统 · 并发与 IO

---

**Q1：死锁的四个必要条件？如何预防、避免、检测、解除？**

**A：** 四个条件**同时成立**才会死锁：

1. **互斥**：资源一次只能被一个进程持有；
2. **占有且等待**：持有一个资源的同时等待另一个；
3. **不可抢占**：资源不能被强行剥夺；
4. **循环等待**：存在进程—资源的环形等待链。

四种对策：

- **预防**（破坏条件）：一次性申请全部资源（破坏 2）、申请不到就释放已持有的（破坏 2/3）、给资源编号按序申请（破坏 4）；
- **避免**（运行时判断）：**银行家算法**，分配前试算是否仍存在安全序列，代价高，实际很少用；
- **检测 + 解除**：定期构建资源分配图找环 → 撤销进程或抢占资源；
- **实际工程做法**：给锁加超时（如 `lock_timeout`）、统一加锁顺序、减小锁粒度、用无锁/乐观并发（CAS、MVCC）。

> MySQL InnoDB 的做法很典型：等待图检测死锁，回滚 undo 量更小的事务；同时 `innodb_lock_wait_timeout` 兜底。

**Q2：互斥锁、自旋锁、读写锁、乐观锁/悲观锁的区别与场景？**

**A：**

- **互斥锁 mutex**：抢不到就睡眠（让出 CPU），适合临界区较长；睡眠/唤醒有上下文切换成本（微秒级）。
- **自旋锁 spinlock**：抢不到就忙等，不让出 CPU，适合临界区极短（几十条指令）的多核场景，省掉切换开销；单核可抢占环境会退化。
- **读写锁 rwlock**：读共享、写独占，适合读多写少；注意写饥饿，可用写优先变体。
- **乐观锁**：不加锁，更新时校验版本（CAS / version 字段 / MVCC），冲突就重试，适合冲突少的场景。
- **悲观锁**：先加锁再操作，适合冲突多、临界区代价高的场景。

> 工程提示：锁粒度从正确性倒推——先保证同一共享资源的修改串行化，再用分段锁（ConcurrentHashMap）、读写锁降低争抢。

**Q3：什么是原子操作 / CAS？ABA 问题怎么解决？**

**A：**

- **原子操作**：不可被打断的指令序列，依赖 CPU 原子指令（x86 的 `lock cmpxchg`、LL/SC）+ 缓存一致性（MESI）。
- **CAS**：`CAS(addr, expect, new)`，仅当 `*addr == expect` 才写入并返回成功；是原子自增、无锁队列、自旋锁的基础。
- **ABA**：值从 A 改成 B 又改回 A，CAS 误判"没变过"（无锁栈弹出时节点被回收复用最典型）。
- 解决：加版本号（`AtomicStampedReference`，比较"值 + 版本"）、hazard pointer、RCU、延迟回收。
- 代价：高竞争时疯狂自旋（CPU 空转），且只能原子改**一个**变量，多变量复合操作仍需锁。

**Q4：同步/异步 与 阻塞/非阻塞 的区别？**

**A：** 两组正交概念，常以"我去买咖啡"类比：

- **阻塞/非阻塞**：**调用方**在等待结果期间是否被挂起。（阻塞：一直等到结果返回；非阻塞：立刻返回，没数据也不等）
- **同步/异步**：**结果通知方式**。（同步：调用方自己取结果；异步：被调用方通过回调/通知/信号把结果"送上门"）

组合举例：

| | 说明 | 例子 |
| --- | --- | --- |
| 同步阻塞 | 一直等到结果 | 默认 `read()`、Java BIO |
| 同步非阻塞 | 立刻返回，自己反复问 | `O_NONBLOCK` + 轮询 |
| 异步非阻塞 | 干别的，好了通知我 | `epoll`/IOCP、Node fs、Go netpoller |
| 异步阻塞 | 理论存在（等通知时被挂起） | 较少见，如 `select` 阻塞等待 |

> 关键：IO 分两段——**等待数据就绪** + **数据从内核拷到用户空间**。非阻塞/多路复用解决第一段，真正的 AIO（如 Linux io_uring、Windows IOCP）才把第二段也异步掉。

**Q5：select / poll / epoll 的区别？**

**A：**

| | select | poll | epoll |
| --- | --- | --- | --- |
| 数据结构 | 固定 `FD_SETSIZE`(1024) 位图 | 数组，无上限 | 内核红黑树 + 就绪链表 |
| 就绪判定 | 每次全量遍历 O(n) | 每次全量遍历 O(n) | 回调只返回就绪 fd，O(1) 取事件 |
| 拷贝 | 每次调用拷贝 fd 集合到内核 | 同左 | `epoll_ctl` 注册一次，之后不拷贝 |
| 触发模式 | 水平触发 LT | LT | LT + **边缘触发 ET** |

- **LT 水平触发**：只要还有数据没读完就一直通知（安全，但可能重复唤醒）；
- **ET 边缘触发**：只在状态变化时通知一次，必须**一次读到底**（循环 read 到 `EAGAIN`），且 fd 需设为非阻塞，效率更高。

> 为什么 epoll 快：不用每次传 fd 集合、不用遍历全部 fd、就绪 fd 由内核回调直接挂到就绪链表。C10K 问题的答案就是 `epoll/kqueue + 非阻塞 IO + 事件循环`。

**Q6：为什么单线程 Redis 能扛 10 万 QPS？**

**A：**

1. 纯内存操作，绝大多数命令 O(1)/O(logN)；
2. **IO 多路复用**（epoll/kqueue）单线程处理海量并发连接，没有线程切换与锁竞争；
3. 数据结构精心设计（SDS、哈希表渐进式 rehash、跳表、ziplist/listpack 省内存）；
4. 无锁、无上下文切换，CPU 缓存友好；
5. 耗时操作被外置：持久化 fork 子进程、删除大 key 用 `unlink` 异步、Redis 6.0 起把**网络 IO 读写**放多线程，命令执行仍单线程。

> 瓶颈与注意：单线程意味着**一条慢命令会阻塞所有请求**（`KEYS *`、大 key 删除、`FLUSHALL`），必须拆分成 `SCAN`/`UNLINK` 分批执行。

**Q7：同步 IO、异步 IO、IO 多路复用、信号驱动 IO 分别是怎样的？**

**A：** 一次网络 `read` 的过程 = 等数据到内核缓冲区 + 从内核缓冲拷到用户空间。

1. **阻塞 IO**：两步都阻塞等待；
2. **非阻塞 IO**：第一步立即返回，需要反复轮询；
3. **IO 多路复用**（select/poll/epoll）：一个线程监听多个 fd，某个就绪了再去 read，第一步阻塞在**多路复用器**上（不是单个 fd），第二步仍阻塞拷贝；
4. **信号驱动 IO**：fd 就绪时内核发 `SIGIO`，应用收到信号再 read，第一步不阻塞；
5. **异步 IO**（AIO / io_uring / IOCP）：两步都交给内核，完成后回调通知，**全程不阻塞**。

> 现实：Linux 早期 glibc AIO 是线程池模拟的、libaio 对网络 fd 支持差，所以高性能网络程序普遍用 **epoll + 非阻塞**（本质是同步 IO，只是"多路复用"）；磁盘 IO 的新方向是 `io_uring`（真正的异步、减少 syscall、支持 SQPOLL）。

**Q8：什么是零拷贝？有哪几种实现？**

**A：** 传统的"读文件 → 发到网络"：`read()` + `write()` 需 **4 次上下文切换 + 4 次数据拷贝**（磁盘→内核页缓存→用户缓冲→socket 缓冲→网卡）。

零拷贝方案：

1. **`mmap` + `write`**：用户缓冲与内核页缓存映射共享，省掉一次用户态拷贝（仍 4 次切换、3 次拷贝）；
2. **`sendfile`**：直接在内核态把页缓存拷到 socket 缓冲，**2 次切换 + 3 次拷贝**（Linux 2.4+ 配合 SG-DMA 可做到 2 次拷贝：页缓存 → 网卡，CPU 完全不参与拷贝）；
3. **`splice`/`tee`**：用管道缓冲在内核里搬运，无需用户态；
4. **`io_uring`**：异步 + 减少系统调用。

应用：Kafka、Nginx（`sendfile on`）、RocketMQ（mmap）的高吞吐都靠它。

**Q9：生产者-消费者问题怎么解？**

**A：** 三个要素：一个互斥量保护缓冲区、两个信号量计数（空位 `empty`、已填 `full`）。

```
semaphore empty = N, full = 0, mutex = 1;
producer: P(empty); P(mutex); 放入; V(mutex); V(full);
consumer: P(full);  P(mutex); 取出; V(mutex); V(empty);
```

> 致命细节：**两个 P 的顺序不能反**。先 `P(mutex)` 再 `P(empty)`，若缓冲区满，生产者会握着锁睡死，消费者永远进不去 → 死锁。工程等价物：Java 的 `BlockingQueue`、Go 的 channel、Node 的背压机制。

**Q10：哲学家进餐问题有哪些解法？**

**A：** 五个哲学家、五根筷子，同时拿起左右两根才能吃饭，全拿左边就死锁。解法：

1. **资源分级（最常用）**：给筷子编号，规定**先拿编号小的再拿编号大的**，破坏循环等待；
2. **限制并发**：最多允许 4 人同时上桌（信号量 = 4）；
3. **同时申请**：只有在左右两根都空闲时才一次性拿起（用一个互斥量保护"取筷子"动作）；
4. **奇偶策略**：奇数号先左后右，偶数号先右后左。

> 映射到工程：数据库加锁顺序必须全局一致，否则多事务互相等锁就是哲学家进餐的现实版。

**Q11：并发与并行的区别？线程池为什么能提速？**

**A：**

- **并发 concurrency**：逻辑上同时处理多件事（单核时间片轮转也能并发）；
- **并行 parallelism**：物理上真的同时执行（需要多核）。

线程池提速的本质：复用线程，**摊薄创建/销毁成本**并**控制并发度**，避免"线程越多越慢"（上下文切换、内存占用、锁竞争）。参数直觉：

- CPU 密集：线程数 ≈ CPU 核数（`N` 或 `N+1`）；
- IO 密集：线程数 ≈ 核数 × (1 + 等待时间/计算时间)，例如等待占比 90% 时可到 `10N`；
- 队列：有界队列防 OOM，但要配合合适的拒绝策略（抛错 / 调用者执行 / 丢弃最旧）。
