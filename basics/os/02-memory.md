# 操作系统 · 内存管理

---

**Q1：为什么需要虚拟内存？**

**A：** 三个核心价值：

1. **隔离与保护**：每个进程看到独立且从 0 开始的连续地址空间，页表项带读写执行权限位，无法越界访问别的进程或内核内存；
2. **超额使用**：程序占用可大于物理内存，暂时不用的页换出到磁盘（swap），用时再换入；
3. **简化编程与共享**：链接器不必关心物理布局；多进程可共享同一物理页（动态库代码段、fork 的 COW 页、mmap 共享内存）。

代价：转换依赖 MMU + 多级页表 + TLB；缺页换页比内存访问慢 5~6 个数量级。

---

**Q2：虚拟地址如何转成物理地址？为什么用多级页表？**

**A：** 虚拟地址拆成「页号 + 页内偏移」：4KB 页时低 12 位即页内偏移，直接搬到物理地址低位；页号经页表查到物理页框号（PFN）。

- 单级页表的问题：32 位 + 4KB 页 = 2^20 项 × 4B = 4MB，每个进程常驻 4MB；64 位不可想象。
- 多级页表（x86-64 四级：PGD/PUD/PMD/PTE）：只为实际用到的区间建表，未用的中间层留空，空间随用量增长。
- 代价：一次转换多次访存 → 靠 **TLB**（页表项缓存）兜底，命中率通常 >99%；未命中时的多级查找叫 page walk。
- ASLR：加载地址随机化，增加攻击难度。

---

**Q3：缺页中断（page fault）是什么？分几种？**

**A：** 访问的虚拟页「未映射」或「权限不足」时 MMU 触发异常，内核处理：

1. **次要缺页 minor**：页已在物理内存（COW 页写入、共享库首次访问、零页分配），只需补页表映射，开销小；
2. **主要缺页 major**：页在磁盘（swap 或 mmap 文件），需 IO 换入（必要时先换出别的页），毫秒级；
3. **非法访问**：地址没映射或权限不对 → `SIGSEGV` 段错误。

流程：陷入内核 → 保存现场 → 校验地址合法性 → 分配页框（不够则置换）→ 读盘/清零 → 填页表 → 恢复现场重执行该指令。

> 生产坑：内存不足时每步都缺页换页，CPU 全在等 IO（**swap 抖动 thrashing**），现象是 load 高、sys CPU 高但吞吐为 0。数据库/Nginx 一般关 swap 或 `swappiness=1`。

**Q4：常见页面置换算法？**

**A：**

- **OPT 最佳**：换出将来最久才用的页，理论最优、不可实现（作基准）；
- **FIFO**：先进先出，简单，但有 **Belady 异常**（页框变多，缺页率反而上升）；
- **LRU 最近最少使用**：符合局部性，效果好；精确实现太贵（每次访存都要动链表）→ 实际用近似；
- **Clock / 二次机会**：环形扫描，访问位为 1 则清 0 跳过，为 0 换出，是 LRU 的廉价近似；
- **LFU**：按访问频次，需老化机制防"历史热页"赖着不走；
- Linux 实际：active/inactive 双 LRU 链表，并区分文件页（干净可直接丢）与匿名页（需 swap）。

**Q5：分页和分段的区别？**

**A：**

| 维度 | 分页 | 分段 |
| --- | --- | --- |
| 单位 | 固定大小（4KB），物理视角 | 变长，逻辑视角（代码/数据/堆/栈段） |
| 目的 | 提高内存利用率、便于换入换出 | 反映程序逻辑结构，便于共享与保护 |
| 碎片 | 只产生**内部碎片**（末页用不满） | 只产生**外部碎片**（段间空隙） |
| 地址 | 一维（页号 + 偏移） | 二维（段号 + 段内偏移，需检查段长） |

x86 实为**段页式**：先分段再分页，但 Linux 基本不用段（把所有段基址设为 0），逻辑上等于纯分页。

**Q6：一个进程的虚拟地址空间是怎么布局的（Linux x86-64）？**

**A：** 从高地址到低地址：

1. **内核空间**（如 `0xFFFF800000000000` 以上）：内核代码、物理内存映射、每个进程的内核栈；用户态不可访问；
2. **栈**：向下增长，存放函数调用帧、局部变量、返回地址，默认 8MB（`ulimit -s`）；
3. **内存映射区 mmap**：动态库、共享内存、大块 `malloc`（> `MMAP_THRESHOLD` 128KB）、文件映射，向下/向上增长；
4. **堆**：向上增长，`brk/sbrk` 或 `mmap` 扩展，`malloc` 的主战场；
5. **BSS 段**：未初始化/初始化为 0 的全局与静态变量（不占文件空间，加载时清零）；
6. **数据段 .data**：已初始化的全局/静态变量（占文件空间）；
7. **代码段 .text**：机器指令，只读可执行；旁边还有 `.rodata` 只读数据（字符串字面量）。

> 32 位系统经典划分是 3G 用户 / 1G 内核；64 位地址空间巨大（目前只用 48 位），用户/内核各 128TB。

---

**Q7：栈和堆的区别？**

**A：**

| 维度 | 栈 | 堆 |
| --- | --- | --- |
| 管理方式 | 编译器自动分配/释放（移动 SP） | 程序员 `malloc/free` 或 GC |
| 生长方向 | 向低地址 | 向高地址 |
| 分配速度 | 极快（一条指令改栈指针） | 慢（要找空闲块、可能系统调用） |
| 大小 | 小（默认 8MB），溢出 → 栈溢出 | 大，受虚拟内存限制 |
| 碎片 | 无 | 有外部碎片 |
| 共享 | 线程私有 | 进程内线程共享 |

> 经典坑：返回局部变量的指针（栈帧已销毁，悬垂指针）；递归深度过大导致栈溢出（`Maximum call stack size exceeded` 也是同源）。

**Q8：`malloc` 是怎么实现的？**

**A：**

- 小块（< 128KB）：用 `brk` 抬高堆顶，在这片区域里切分。glibc 用 **ptmalloc2**：按大小分成 fast bins / small bins / large bins / unsorted bin 等空闲链表，分配时找合适 chunk，释放时合并相邻空闲 chunk（防碎片）。
- 大块（≥ `M_MMAP_THRESHOLD`，128KB）：直接 `mmap` 匿名映射，free 时 `munmap` 立刻归还 OS。
- chunk 头部带 size/标志位（复用相邻块信息），所以 `malloc(1)` 实际占用 16~32 字节。
- 多线程：每个线程有独立 arena，减少锁竞争。

> 常见误解：`free(p)` 后内存**不一定**立刻还给 OS，可能留在分配器的空闲链表里复用 → RSS 不降。这与内存泄漏要区分（可用 `malloc_trim` 或换 jemalloc/tcmalloc）。

---

**Q9：内存碎片是什么？怎么缓解？**

**A：**

- **内部碎片**：分配了但没用满（页内剩余、malloc 对齐与头部的额外开销）；
- **外部碎片**：空闲内存总量够，但被切成不连续的小块，无法满足大块请求。

缓解：
1. 分页（消除外部碎片，只剩内部碎片）；
2. 伙伴系统（buddy）按 2 的幂分配与合并 —— 内核页级分配；
3. Slab/Slub 分配器：为内核小对象（如 `task_struct`）做对象缓存，既快又减少碎片；
4. 用户态用更优分配器：jemalloc（Redis/FreeBSD）、tcmalloc（Google）按 size class 分桶 + 线程缓存；
5. 应用层：对象池/内存池、避免频繁大小混搭的分配释放。

**Q10：OOM 是怎么发生的？Linux 的 OOM Killer 选谁杀？**

**A：** 内存耗尽且无法回收（页面缓存已压不出、swap 也满）时，内核调用 OOM Killer 挑一个进程杀掉以自保。选择依据是 **oom_score**：主要由进程占用内存比例决定，加上 `oom_score_adj`（范围 -1000~1000，-1000 表示禁止被杀）与特权进程减分。关键服务（数据库、SSH）可以 `echo -1000 > /proc/<pid>/oom_score_adj` 保护。

> 容器场景注意：cgroup 内存超限触发的是 **cgroup OOM**，杀的是该 cgroup 内 oom_score 最高的进程，与宿主机全局 OOM 不同；K8s 里表现为 Pod 被 OOMKilled（`exit code 137`）。
