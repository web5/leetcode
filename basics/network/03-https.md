# 计算机网络 · HTTPS / TLS 与中间人攻击

---

**Q1：HTTPS 是怎么建立连接的？整体分几步？**

**A：** HTTPS = HTTP over TLS（默认 443 端口）。从"啥都没有"到"能安全传数据"，一共三段：

```
1) TCP 三次握手    → 先把路修通（注意：三次握手本身不加密）
2) TLS 握手        → 双方商量出一把「临时对称密钥」
3) 应用数据传输    → 所有 HTTP 报文用这把对称密钥加密 + 完整性校验
```

也可以画成这样，理解代价在哪：

```
DNS 解析 → TCP 握手(1 RTT) → TLS 握手(1~2 RTT) → 加密通信
```

> 追问"HTTPS 慢在哪"：主要慢在**握手阶段的 RTT**（一个来回就是一个 RTT，跨国链路一个 RTT 可能 100ms+）。数据加密本身因为有 AES-NI 硬件指令，CPU 开销可以忽略。所以优化方向是**减少 handshake 次数**：TCP Fast Open、TLS 1.3 的 1-RTT、会话复用的 0-RTT、以及连接池复用已有连接。

---

**Q2：TLS 握手具体在干什么？（TLS 1.2 完整流程）**

**A：** 以最常用的 **TLS 1.2 + ECDHE** 为例（RSA 密钥交换已淘汰，原因见 Q4）：

| 步骤 | 谁发的 | 内容 |
| --- | --- | --- |
| 1 | 客户端 → 服务端 | `ClientHello`：支持的 TLS 版本、密码套件列表、随机数 `Client Random`、SNI（要访问的域名） |
| 2 | 服务端 → 客户端 | `ServerHello`：选定版本与套件、随机数 `Server Random` |
| 3 | 服务端 → 客户端 | **证书链**（含服务端公钥）、`ServerKeyExchange`（ECDHE 参数 + 服务端签名）、`ServerHelloDone` |
| 4 | 客户端（本地） | **校验证书**：签发链、域名、有效期、吊销状态 |
| 5 | 客户端 → 服务端 | `ClientKeyExchange`：自己的 ECDHE 公钥参数（也可能为空，取决于算法） |
| 6 | 双方各自计算 | 用 ECDHE 算出相同的**预主密钥**，结合两个随机数派生出**会话密钥**（对称密钥） |
| 7 | 双向 | `ChangeCipherSpec` + `Finished`（加密的那份），验证前面所有握手内容**没被篡改** |
| 8 | — | 之后全用对称密钥传数据 |

一句话总结：**握手用非对称，传数据用对称。**

> 关键点：`Finished` 消息是对**前面所有握手报文**做的摘要。这意味着中间人哪怕只改了握手阶段里一个比特（比如把套件降级成弱算法），双方算出来的 Finished 也会不匹配，握手直接失败。

---

**Q3：为什么非对称只用在握手，数据要用对称加密？**

**A：** 纯粹是**性能**问题：

| | 非对称加密（RSA/ECC） | 对称加密（AES-GCM / ChaCha20） |
| --- | --- | --- |
| 密钥 | 公钥可以公开，私钥保密 | 双方共享同一把密钥 |
| 速度 | **慢**（大数/椭圆曲线运算），且有 AES-NI 之外的硬件开销 | **快**（有 AES-NI 硬件加速，吞吐可达 GB/s） |
| 用途 | 解决"双方如何在不加密的信道里安全地协商出密钥" | 解决"大量数据怎么高效地加密" |

所以标准做法是：**用非对称（或 DH）安全地交换一把临时的对称密钥，然后用它加密剩下的所有数据。**

> 顺带澄清一个常见误解：**服务器的私钥从来不参与数据加密**。它只在握手时被用来「签名」证明身份（以及旧式 RSA 套件里用来解密预主密钥）。真正加密数据的是会话密钥。

---

**Q4：什么是前向安全（PFS）？为什么 RSA 密钥交换被淘汰了？**

**A：**

- **RSA 密钥交换（TLS 1.2 旧方式）**：客户端生成预主密钥，**用服务器公钥加密后发给服务端**。风险在于：会话密钥完全由这一个密文决定，**只要服务器私钥将来某天泄露**，黑客就能解开它录下来的全部历史流量 —— 「先录制，后解密」。
- **ECDHE（前向安全）**：双方各自生成临时密钥对，交换公钥后各自算出同一个共享密钥。**会话密钥不会在网络上传输，也不依赖服务器私钥**。就算私钥泄露，也只能用于**冒充身份**（伪造签名），解不开以前录制的流量。

> 这就是 TLS 1.3 直接砍掉 RSA 密钥交换、只保留 DHE/ECDHE 的原因：**所有连接都强制前向安全**。所以服务器必须正确保管私钥，同时也要考虑到：没有 PFS 的话，"现在没事"不等于"以后没事"。

---

**Q5：TLS 1.3 相比 TLS 1.2 改了什么？（高频追问）**

**A：**

| 维度 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 握手速度 | 2-RTT（完整） | **1-RTT**（ClientHello 直接带上猜测的 DH 参数，省一个来回） |
| 会话恢复 | Session ID / Session Ticket | **PSK + 0-RTT**（恢复会话时第一个数据包就能带业务数据） |
| 前向安全 | 部分套件支持 | **强制**（只保留 ECDHE/DHE，删除 RSA 密钥交换和静态 DH） |
| 算法清理 | 支持 RC4、3DES、CBC（带各种漏洞）、SHA-1、MD5 | 大幅精简，只留下 AEAD 类套件（AES-GCM / ChaCha20-Poly1305） |
| 握手加密 | ServerHello 之后仍是明文（证书可被看） | **ServerHello 之后就加密**，证书也加密传输（隐私更好） |
| 密码协商 | 协商过程可被降级攻击篡改 | 协商内容也参与 Finished 校验 |

> 0-RTT 的代价（追问点）：0-RTT 数据用的是上一次会话的 PSK，**不具备前向安全**，而且**可能重放**（同一个 0-RTT 请求可能被攻击者重放多次）。所以规范建议：**不要对 0-RTT 数据执行非幂等操作**（别在里面转账/下单），只在 GET 这类幂等请求上用。

**Q6：证书里到底有什么？客户端具体校验证书的哪些东西？**

**A：** 这是防中间人攻击的**核心**，必须能背下来四条：

1. **签发链可信**：证书是被谁签的？逐级往上找，**最终要能落到浏览器/操作系统内置的某个根证书**（信任锚）。自建 CA、未收录的中间证书都会校验失败。
2. **域名匹配**：证书的 `CN` / `SAN（Subject Alternative Name）` 字段必须包含你正在访问的域名。通配符 `*.example.com` **只对同级子域有效**，不匹配 `a.b.example.com`。
3. **在有效期内**：包含 `Not Before` / `Not After`，另外浏览器对有效期上限也有限制（现在最长 398 天）。
4. **未被吊销**：通过 **CRL**（证书吊销列表，要下载全量，慢）或 **OCSP**（实时查单个证书状态）确认。**OCSP Stapling**（服务器在握手时带上自己的 OCSP 响应）是最优解 —— 客户端不用自己去查询，又快又保护隐私。

证书的组成：`持有者信息（域名/组织）` + `持有者公钥` + `签发者` + `有效期` + `序列号` + `扩展字段（SAN、用途、CA 标记）` + `CA 的数字签名`。

**校验的本质**：CA 用自己的**私钥**对证书内容签名，浏览器用 CA 的**公钥**验签。攻击者没有 CA 私钥，就伪造不出一张能通过校验的证书 —— 这是整套体系的地基。

> 追问"为什么不能直接信服务端给的公钥"：因为它没法自证身份，任何人都能生成一对密钥冒充。**CA 的作用是"第三方背书"**：把"身份证明"这件事委托给一个大家都预先信任的机构。注意这是**集中式信任**，所以才有了下面 Q10 里的那些缓解机制（CT、CAA）。

**Q7：HTTPS 一定安全吗？**

**A：** **不一定。** HTTPS 只保证「管道这一段」的三件事，超出这个范围它就管不着了：

| HTTPS 保证 | 说明 |
| --- | --- |
| 机密性 | 中间人看不到内容（用户名、密码、信用卡号） |
| 完整性 | 内容改不了，改了会被 AEAD 的校验标签检出，连接直接断 |
| 身份认证 | 你连的确实是你以为的那个域名背后的服务器（**前提是证书校验正确**） |

但下面这些场景，HTTPS **保护不了**：

1. **端点被攻破**：你手机上装了恶意 App / 木马 —— 它在数据加密之前就看到了明文。HTTPS 保护的是传输过程，**保护不了设备本身的安全**。
2. **你自己忽略了证书警告**：浏览器弹「证书不受信任，是否继续」，你点了"继续" —— 等于主动把钥匙递给陌生人。
3. **设备上被装了流氓根证书**：企业监控网关、抓包工具的描述文件、恶意根证书。只要你信任了这张根证书，它签什么你都认，**HTTPS 完全失效**。这是中间人攻击在现实中最常见的形态。
4. **CA 被攻破或滥签发**：历史上真实发生过（如 DigiNotar 被入侵后给 google.com 发了伪造证书）。靠 **证书透明度（CT）** 事后发现。
5. **钓鱼网站同样有 HTTPS**：现在几乎每个钓鱼站都能免费申请到 Let's Encrypt 证书。**地址栏那把锁只表示"你和这个服务器的连接是加密的"，不代表"这个网站是正规的"** —— 要看域名。
6. **TLS 在中途就被卸载了**：大流量站点一般在 CDN / 负载均衡 / API 网关做 TLS 卸载，后面内网微服务之间是 HTTP 明文。**内网一旦被渗透，HTTPS 一点用没有**（所以内部服务需要 mTLS 或至少严格的微隔离）。
7. **协议/实现有漏洞**：协议面有过 POODLE、BEAST、FREAK/Logjam、重协商漏洞；实现面有过心脏出血（Heartbleed）。现在普遍禁用 SSLv3 / TLS 1.0 / 1.1，TLS 1.2 也要配好套件。
8. **元数据依然泄露**：即使内容是加密的，**目标域名**（明文 SNI，除非启用 ECH）、**目标 IP**、以及**数据包的大小和时序**仍可能被分析推断（流量指纹攻击可以猜出你在看哪个视频）。

一句话：**HTTPS 防的是"管道上的窃听和篡改"，防不了"端点的妥协"和"用户脑子里的信任判断"。**

**Q8：中间人攻击（MITM）的原理是什么？**

**A：** 攻击者把自己**插到你和服务器之间，冒充双方** —— 对你假装是服务器，对服务器假装是你：

```
你 ──TLS──> 攻击者 ──TLS──> 真实服务器
             （伪装）
    ←— 两端各建一条合法的 HTTPS 连接，但中间人是明文中转站
```

瞄准的就是「身份认证」这个环节：**只要你肯相信攻击者出示的证书，他就成功了。**

攻击要成立通常需要两个前提之一：

1. **伪造/盗用了证书**：攻击者通过攻破 CA、欺骗 CA 签发、或者直接盗走私钥，拿到一张能通过校验的证书；
2. **客户端被植入了恶意根证书**（最常见）：公司网关、抓包工具、恶意描述文件。这种情况下攻击者可以随时给自己签一张任何域名的证书，你的设备会全盘信任。

常见的 MITM 手法：

- **ARP 欺骗 / DNS 劫持 / 伪造 Wi-Fi 热点**：把你引到攻击者机器上；
- **SSL Stripping（降级攻击）**：攻击者把你在 HTTP 阶段的请求全部保持 HTTP，不跳 HTTPS —— 让你从头到尾都是明文。这是 **HSTS** 主要解决的问题；
- **SSL Splitting**：上面提到的「两条 TLS 连接中间中转」；
- **证书伪造**：伪造签发链冒充目标域名。

> Charles / Fiddler / mitmproxy 抓 HTTPS 包的原理就是第 2 条 —— 你在设备上**主动安装并信任了它的根证书**。这也是为什么"能抓到包"不代表 HTTPS 不安全，**只代表你主动授权了一台中间人的机器**。

**Q9：中间人攻击怎么防？**

**A：** 按责任方分层：

**客户端 / 浏览器侧（最关键的防线）**

- **严格校验且绝不忽略证书错误**（根基中的根基）：上面 Q6 那四条一条都不能少。
  > 生产事故重灾区：代码里写了 `verify=False`、`requests` 关掉证书验证、`curl -k`、Android 里覆写 `TrustManager` 空实现放行所有证书 —— 这些写法等于把 HTTPS 的防线整个拆掉，比不用 HTTPS 还危险（因为看起来是安全的）。
- **HSTS**（`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`）：告诉浏览器"以后这个域名只准走 HTTPS"。有了它，即使用户手输 `http://` 或遭遇 SSL Stripping 也不生效；
  - 配合 **HSTS Preload 列表**（内置到浏览器里）可以把"首次访问"这个空窗期也覆盖掉。
- **证书透明度（CT）**：所有公开签发的证书必须进公开日志。域名所有者可以通过 crt.sh 等监控服务发现自己是否被冒名签发了证书；现代浏览器也会强制要求公开证书带 CT 信息（SCT），否则不信任。
- **不安装来源不明的根证书 / 描述文件**（用户层面最重要的一条）。

**服务端 / 运维侧**

- 全站 HTTPS + **301 跳转**，别留 HTTP 可用的后门；
- 启用 **HSTS** + Preload、**OCSP Stapling**；
- 配 **CAA DNS 记录**：限定只有某个 CA 能给这个域名签证书，防止其它 CA 被利用误签；
- 加固 TLS 配置：只留 **TLS 1.2 / 1.3**，禁用弱套件，保证前向安全（用 ECDHE）；可以上 SSL Labs 测分，目标 A+；
- DNS 层面加固（**DNSSEC**、DoH/DoT）：域名本身被劫持了证书也白搭。

**特殊场景的额外手段**

- **双向 TLS（mTLS）**：不只你校验服务端，**服务端也校验你的客户端证书**。这样中间人连"冒充客户端"都做不到（拿不到合法客户端证书）。内部服务、Open API 对接、服务网格（Istio / Linkerd）里大量使用。
- **证书固定（Certificate Pinning）**：App 里硬编码"我只认这张证书 / 这个公钥"，伪造的 CA 证书一律不认。金融类 App 的常见做法。
  > Web 上的 **HPKP 响应头已经被浏览器废弃**（一旦配错会把自己的站点彻底锁死），现在只在**原生 App 里自行实现** pinning，且必须留备用引脚和应急更新通道。

**普通用户能做的**：不装陌生根证书 / 描述文件；肉眼核实**域名本身**而不是只看那把锁；公共 Wi-Fi 下少做敏感操作。

**Q10：为什么已经有了 CA 体系，还需要 CT、CAA 这些东西？**

**A：** 因为 CA 是**集中式信任**：全球上百个 CA，任何一个出问题（被攻破、操作失误、被人骗签、内部作恶），都能给任意域名签发合法的证书。所以后来加了一圈「制衡」机制：

| 机制 | 解决什么 | 在哪一层 |
| --- | --- | --- |
| **CT（证书透明度）** | 所有签发进公开日志，**事后能发现**被冒名签发 | 浏览器强制 + 域名主自己监控 |
| **CAA（DNS 记录）** | 限定**只有哪个 CA 允许签发**，事前收窄 | DNS |
| **吊销（CRL / OCSP）** | 签发错了**能撤销** | 校验时实时查询 |
| **缩短有效期（现在最长 398 天）** | 证书失陷后**危害窗口变小** | 签发策略 |
| **HSTS + Pinning** | 即使拿到假证书也**不被采信** | 客户端 / App |

> 这五个叠起来能看出来，现代的防线思路已经从"完全信任 CA"转向了"**假设 CA 也可能出错**"。

**Q11：HTTPS 常见误解澄清（追问高频）**

**A：**

1. **"我有证书就安全了"** —— 证书只提供**身份认证**。安不安全还要看 TLS 版本、加密套件、私钥保管、是否真的做了证书校验。
2. **"HTTPS 会拖慢性能"** —— 现代 TLS 1.3 握手只要 1 个 RTT，会话复用甚至 0-RTT；加密本身有 AES-NI 硬件加速。真实瓶颈一般是**握手 RTT** 和**连接管理**，不是加密。
3. **"HTTPS 的数据绝对不可破解"** —— 只要在你的设备上装了它的根证书，Charles / mitmproxy 就能看明文。这说明 HTTPS 的安全前提是 "**我不信任这台机器**" 不成立时就失效了。
4. **"用了 HTTPS 就不用再做其它安全了"** —— 它不防 XSS、不防 CSRF、不防 SQL 注入、不防业务逻辑漏洞。HTTPS 只是把管道包起来，管道里装什么它不管。
5. **"免费证书 = 不安全"** —— Let's Encrypt 这类 DV 证书提供的加密强度和企业级证书完全一样，只是**验证的严格程度**不同（DV 只验证域名控制权，OV/EV 会验证组织实体身份）。敏感场景（银行/支付）在意的是 EV 带来的组织背书，不是加密强度。

**Q12：排查 HTTPS 问题常用哪些命令？**

**A：**

```bash
# 看完整握手过程、证书链、协商出的套件
openssl s_client -connect example.com:443 -servername example.com

# 只看证书（含有效期、SAN、签发者）
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer -ext subjectAltName

# 测某个协议是否被支持（能握手成功说明该版本未禁用）
openssl s_client -tls1 -connect example.com:443
openssl s_client -tls1_2 -connect example.com:443

# 忽略证书校验错误（仅本地排错用！生产代码里绝不能这么写）
curl -k https://example.com

# 明确指定信任的 CA bundle（脚本/CI 里推荐，避免误把自签 CA 混进来）
curl --cacert /path/to/ca.pem https://example.com

# 看 HTTP -> HTTPS 是否 301 跳转、HSTS 头是否下发
curl -I http://example.com
curl -I https://example.com

# 顺便测 HTTP/2、HTTP/3 是否已启用
curl -I --http2 https://example.com
curl -I --http3 https://example.com
```

> 排查口诀：**证书报错先看 SAN 里的域名是否包含你要访问的域名**，再看**中间证书是否配全**。缺中间证书是运维最常见的配置故障，典型表现是：浏览器能正常访问（浏览器会自动补链），但 `curl` / Java / Go 客户端报 `unable to get local issuer certificate`。开发环境可以临时用自签 CA（把根证书加进 `--cacert`），但上线前必须换成正规签发链的证书。
