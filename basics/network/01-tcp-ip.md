# 计算机网络 · TCP/IP

---

**Q1：OSI 七层模型和 TCP/IP 四层模型分别是什么？各层协议有哪些？**

**A：**

| OSI 七层 | 功能 | 典型协议 | TCP/IP 四层 |
| --- | --- | --- | --- |
| 应用层 | 为用户提供服务 | HTTP、HTTPS、DNS、FTP、SMTP、SSH、WebSocket | 应用层 |
| 表示层 | 数据格式/加密/压缩 | TLS（常归入应用层）、JPEG、SSL | 应用层 |
| 会话层 | 建立/管理/终止会话 | RPC、NetBIOS | 应用层 |
| 传输层 | 端到端可靠/不可靠传输 | **TCP、UDP** | 传输层 |
| 网络层 | 寻址与路由 | **IP、ICMP、ARP（介于二三之间）、OSPF、BGP** | 网际层 |
| 数据链路层 | 相邻节点帧传输 | 以太网、PPP、交换机（MAC） | 网络接口层 |
| 物理层 | 比特流/电信号 | 网线、光纤、集线器 | 物理层（常并入接口层） |

> 白话版：应用层决定"发什么"，传输层决定"怎么可靠地端到端送"，网络层决定"走哪条路"，链路层决定"下一跳给谁"。

**Q2：TCP 三次握手的报文与状态变化？**

**A：**

```
C: CLOSED → SYN-SENT      SYN, seq=x
S: LISTEN → SYN-RCVD      SYN+ACK, seq=y, ack=x+1
C: SYN-SENT → ESTABLISHED ACK, seq=x+1, ack=y+1
S: SYN-RCVD → ESTABLISHED
```

核心目的：**双方各自确认自己的初始序列号（ISN）被对方收到**，即双向确认通信能力。第三次握手已经可以携带应用数据（`TCP Fast Open` 更进一步，首包就带数据）。

---

**Q3：为什么是三次握手，两次不行吗？**

**A：** 两次握手最大的问题是**历史重复连接**。若客户端发出的旧 SYN 因网络滞留后到达服务端：

- 两次握手：服务端回 SYN+ACK 后**直接建立连接并分配资源**，但这个连接客户端根本不认（它期待的是新连接的 ISN），服务端白白等死；
- 三次握手：客户端收到后发现自己期待的 ack 对不上，回 **RST** 终止，避免服务端建立错误连接。

另外，两次握手也让服务端无法确认自己的 ISN 是否被对方收到。**总结：三次是"确认双方收发能力都正常"的最小值。**

---

**Q4：四次挥手的过程？为什么需要四次？**

**A：**

```
主动方 FIN_WAIT_1  ──FIN──▶                     被动方 ESTABLISHED
                   ◀──ACK──                     CLOSE_WAIT
主动方 FIN_WAIT_2                                （继续发剩余数据）
                   ◀──FIN──                     LAST_ACK
主动方 TIME_WAIT ──ACK──▶                        CLOSED
（等 2MSL 后 CLOSED）
```

之所以要四次：TCP 是**全双工**，每个方向要单独关闭。被动方收到 FIN 时可能还有数据没发完，只能先回 ACK（"我知道你要关了"），等数据发完再发自己的 FIN，因此 ACK 和 FIN 分开发。

---

**Q5：为什么要有 TIME_WAIT？为什么要等 2MSL？**

**A：**

1. **可靠地终止连接**：最后一个 ACK 可能丢失，被动方会重发 FIN；若主动方已关闭，就只能回 RST，导致对方异常报错。留 TIME_WAIT 可重发 ACK。
2. **让旧连接的残留报文在网络中消散**：避免相同四元组的新连接收到旧报文（序列号错乱）。

`2MSL` = 报文最大生存时间（MSL，Linux 默认 30s，故 TIME_WAIT 60s）的两倍 = 「去程 ACK + 回程 FIN」的最坏往返。

> 服务端大量 TIME_WAIT 的应对（短连接场景）：`net.ipv4.tcp_tw_reuse=1`（客户端复用）、`SO_LINGER` 慎用、改成长连接/连接池。注意 `tcp_tw_recycle` 在 NAT 环境下会丢包，Linux 4.12 已移除。

---

**Q6：TCP 如何保证可靠传输？**

**A：** 六个机制：

1. **序列号 + 确认应答（ACK）**：每个字节有编号，接收方按序确认；
2. **超时重传**：RTO 基于 RTT 动态计算（Jacobson 算法），超时重发；
3. **快速重传**：收到 3 个重复 ACK 就立刻重传丢失段，不等超时；
4. **滑动窗口**：批量发送、按序交付 + 流量控制；
5. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复（见 Q8）；
6. **校验和**：检测传输错误，出错直接丢弃。

> 补充：**SACK**（选择性确认）只重传真正丢失的段，避免"重传一个就要重传之后所有"的浪费。

---

**Q7：TCP 的流量控制与拥塞控制有什么区别？**

**A：**

- **流量控制**：保护**接收方**不被发爆。接收方在窗口字段里通告自己的 `rwnd`（接收缓冲区剩余），发送方发送量 ≤ `rwnd`。窗口为 0 时会启动零窗口探测。
- **拥塞控制**：保护**网络**不被打爆。发送方维护 `cwnd`（拥塞窗口），根据丢包/延迟感知网络状况动态调整。

实际发送窗口 = `min(cwnd, rwnd)`。

---

**Q8：拥塞控制四个阶段？**

**A：**

1. **慢启动**：`cwnd` 从 1 MSS 起，每收到一个 ACK 就 +1 MSS → 每 RTT 翻倍（指数增长），直到 `ssthresh`；
2. **拥塞避免**：超过 `ssthresh` 后每 RTT 只 +1 MSS（线性增长）；
3. **快重传**：收到 3 个重复 ACK，立即重传丢失段，不等 RTO；
4. **快恢复**：`ssthresh = cwnd/2`，`cwnd = ssthresh`（而非回到 1），直接进入拥塞避免 —— 因为还能收到重复 ACK 说明网络没死透。

若发生**超时重传**（更严重）：`ssthresh = cwnd/2`，`cwnd = 1`，重新慢启动。

> 现代默认算法是 **CUBIC**（Linux，用三次函数逼近，长肥管道吞吐更好）；Google 的 **BBR** 改为按带宽-延迟积（BDP）建模，不把丢包当拥塞信号，弱网/长链路下吞吐更高。

**Q9：TCP 和 UDP 的区别？UDP 用在哪？**

**A：**

| | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（三握四挥） | 无连接 |
| 可靠性 | 可靠（重传、排序、去重、流控、拥塞控制） | 尽最大努力交付，不保证 |
| 传输单位 | 字节流（无消息边界 → **粘包**） | 数据报（保留边界） |
| 头部 | 20~60 字节 | 8 字节 |
| 速度/延迟 | 慢、延迟抖动大 | 快、实时 |
| 连接数 | 一对一，一条连接占内核资源 | 一对一/多播/广播 |

UDP 适用场景：音视频（RTP/WebRTC）、实时游戏、DNS 查询、**QUIC/HTTP3**、广播与多播。

> 常见追问："UDP 怎么做到可靠？"——在**应用层**补上 TCP 那套：序列号、ACK、重传、流控（QUIC 就是这么干的，还顺便解决了队头阻塞）。

**Q10：什么是 TCP 粘包/拆包？怎么解决？**

**A：** TCP 是**字节流**协议，没有消息边界，"粘包"本质是接收方不知道一条消息的起止：

- 发送方：Nagle 算法/缓冲合并多个小包一起发（粘）；
- 接收方：读缓冲区时可能一次读到半条或多条消息（拆/粘）。

解决方案（都是**应用层**约定）：

1. **定长消息**（简单但浪费）；
2. **分隔符**（如 `\n`、HTTP 的 `\r\n\r\n`），需注意转义；
3. **长度前缀**（最常用）：消息头 4 字节表示 body 长度 —— protobuf、Dubbo、Redis RESP 都用这个；
4. 复杂协议用自定义帧格式（HTTP/2 的帧头带 length + type + flags）。

> 补充：`TCP_NODELAY` 关掉 Nagle 只解决"发送合并"，不解决接收侧边界问题。

**Q11：SYN Flood 攻击是什么？如何防护？**

**A：** 攻击者只发 SYN 不回 ACK，服务端为每个 SYN 分配连接资源并等待（SYN_RCVD），半连接队列被打满后正常用户建连失败。

防护：

1. **SYN Cookie**：服务端不在半连接队列里存状态，而是把连接信息编码进 SYN+ACK 的初始序列号，收到 ACK 时反算校验（Linux 默认在队列满时启用）；
2. 增大 `tcp_max_syn_backlog`、减小 `tcp_synack_retries`（少重传、早释放）；
3. 上游 DDoS 高防/限流（SYN rate limit）；
4. 全连接层面：`somaxconn` + 应用 `listen(backlog)` 一起调大。

---

**Q12：TCP 的半连接队列与全连接队列？**

**A：** 一次连接建立经过两个队列：

- **半连接队列（SYN queue）**：收到 SYN、回 SYN+ACK 后等待 ACK 的连接（SYN_RCVD）；
- **全连接队列（accept queue）**：三次握手完成、等待应用 `accept()` 取走的连接（ESTABLISHED）。

问题定位：全连接队列满会丢弃 ACK 或发 RST，表现为**连接超时/被拒**且服务端 `ss -lnt` 看到 `Recv-Q` 持续高、`netstat -s` 里 `times the listen queue of a socket overflowed` 持续增长。调优：`net.core.somaxconn`（默认 128/4096）、应用 `backlog`、Nginx `backlog` 参数。

**Q13：IP 分片与 MTU/MSS 的关系？**

**A：**

- **MTU**：链路层一次能承载的最大 IP 包，以太网默认 1500 字节；
- **IP 分片**：IP 包大于 MTU 时，路由器/发送方按 MTU 分片（每片带标识、偏移、MF 标志），在**目的端**重组；任一分片丢失则整个包作废（所以分片很伤性能）；
- **MSS**：TCP 层协商的**单个 TCP 段数据部分**上限 = MTU − IP头(20) − TCP头(20) = 1460，在三次握手时通过 options 通告，目的就是**避免 IP 分片**；
- **PMTUD**：路径 MTU 发现（DF=1 探测），收到 `ICMP 需要分片` 时调小 MSS；若 ICMP 被防火墙屏蔽 → "黑洞连接"（大包卡住，小包正常），此时可开 `tcp_mtu_probing` 或手动降 MTU（VPN/隧道常见）。
